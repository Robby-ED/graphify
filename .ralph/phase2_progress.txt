## Codebase Patterns

- Content-sniffed ingestors (mcp_ingest, manifest_ingest, dbt_manifest_ingest) live as
  top-level `graphify/*.py` siblings, NOT under `graphify/extractors/` — that directory is
  for suffix-dispatched per-language extractors only (see `graphify/extractors/MIGRATION.md`).
- Dispatch precedence in `_get_extractor` (graphify/extract.py): filename/content-sniffed
  checks (blade, mcp config, dbt manifest, package manifest, ObjC/C++ header sniffing) all
  run BEFORE the generic `_DISPATCH.get(path.suffix)` fallback. Order among the sniffed
  checks only matters where a real collision risk exists; document why when there isn't one.
- Cross-extractor node-ID collapsing (for `graphify merge-graphs`) is achieved purely by
  using `make_id(bare_name)` — no special-cased edge type needed. lookml.py's
  `sql_table_name` table nodes and dbt_manifest_ingest.py's model/source nodes both use this,
  so a LookML view's backing table and a same-named dbt model resolve to one graph node.
- Baseline full suite before this phase: 2788 passed, 3 skipped, 0 failed, ~85s.
- `uv run` on this project silently bumps `uv.lock`'s own package version line
  (graphifyy 0.9.x) as a side effect — this is unrelated to any code change; do not stage it
  into a feature commit unless intentionally bumping the version.

**Body:**
```markdown
## What

Adds a dbt `target/manifest.json` lineage extractor. dbt models are Jinja templates
(`{{ ref(...) }}`, `{{ source(...) }}`) that graphify's tree-sitter-sql extractor can't
parse — Jinja isn't valid SQL, and dbt only adds the `CREATE TABLE/VIEW` wrapper at run
time, never in the source `.sql` file (verified empirically: running `extract_sql` against
real dbt model files produces a bare file node with 0 edges). dbt itself already resolves
this lineage on every `compile`/`run`/`parse` into `manifest.json`'s `depends_on.nodes`, so
this extractor reads that directly instead of re-deriving it.

## How it works

- `graphify/dbt_manifest_ingest.py` (new, top-level sibling to `manifest_ingest.py` /
  `mcp_ingest.py` — content-sniffed, not suffix-dispatched, so it lives outside
  `graphify/extractors/`):
  - `is_dbt_manifest_path`: filename `manifest.json` AND a 4KB content sniff for
    `dbt_schema_version`, so it never misfires on the unrelated PWA-manifest.json format
    (same filename, totally different schema).
  - `extract_dbt_manifest`: one node per `model`/`seed`/`snapshot`/`source`, keyed by bare
    name via `make_id(name)` (matches `lookml.py`'s `sql_table_name` convention — this is
    what lets `graphify merge-graphs` collapse a dbt model and a same-named LookML view's
    backing table into one node across repos). `depends_on` edges between them.
    `test`/`analysis` resource types excluded (assertions, not physical lineage — a real
    1630-node manifest had roughly as many tests+analyses as models).
- `graphify/extract.py`: facade re-export + dispatch precedence check in `_get_extractor`,
  ahead of the generic package-manifest check (both are content/filename-sniffed gates that
  must win over suffix dispatch).

## Testing

- `tests/test_dbt_manifest.py`: 6 new tests (content-sniff routing incl. PWA-manifest
  negative case, model/source node presence, `depends_on` edge direction, test/analysis
  exclusion, missing-file empty result, no-dangling-edges invariant).
- Full suite: 2794 passed, 3 skipped, 0 failed (was 2788/3/0 before this PR).
- `ruff check` clean.
- Manually smoke-tested (read-only) against a real production dbt project's
  `target/manifest.json` (1630 raw nodes): extractor found 905 lineage nodes / 1394 edges
  (confirms filtering, not a no-op) with zero errors, and reproduced a specific known-correct
  lineage edge end to end.

## Notes for reviewer

- No new dependency — uses only `json` + `pathlib` (stdlib).
- Companion to the LookML extractor on `feat/lookml-extractor` — ships as a separate PR per
  this repo's one-feature-per-PR convention; the shared bare-name `make_id` scoping is what
  lets the two combine cleanly via `merge-graphs` once both land.
```
